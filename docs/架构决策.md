# PlaneWar 架构决策

> 说明**为什么这么设计**以及**改代码时必须遵守什么**。
> 当前代码形态见 `项目结构.md`；组件生命周期等强制规范见 `.workbuddy/memory/cocos-lifecycle.md`。

## 一、设计原则

1. **角色是数据，不是代码**：加一架飞机 = 一个数值文件 + 登记一行 + 放资源，不写新的逻辑类。
2. **唯一真源是 id**：任何跨文件关联一律用 `shipId` 字符串，不用数组下标 ——
   下标对错了不报错，只会悄悄换错资源。
3. **共享算法，就近数值**：算法收敛到 `emitters/`，数值写在各自飞船文件里。
4. **派生值现算**：`maxHp` / `speed` / 外观由 `shipId` 推出，不在运行时数据里存第二份。
5. **表现不回写逻辑**：特效、UI 只消费状态，不影响伤害结算。
6. **特异逻辑有逃生舱**：宁可为某个机型加一个可选钩子，也不往通用基类里塞 `if (shipId === ...)`。

## 二、飞船：一船一类，组合而非继承

每架飞船是一个**独立数据文件**（`ShipRed` / `ShipGreen` / `ShipBlue`），
内含数值、档位表、发射器装配、资源路径。**没有公共基类**。

- 为什么不继承：三架飞机的差异是"数值 + 装了哪些发射器"，不是"同一套行为的重写"。
  继承会把差异固化成类层次，加一架飞机就要加一个子类并复制公共逻辑。
- 为什么值得为 3 架飞机拆 3 个文件：文件结构按**未来的扩展点**切，不按当前行数切。
  下一步必然要做机型专属机制，那时 `ShipRed.ts` 就是它天然的家。

## 三、发射器：组合优于分派

一次开火 = 遍历该机型的 `emitters` 逐个 `tick`。

- **`Emitter.tick()` 返回 `void`，自己去执行**，而不是返回子弹参数数组。
  后者把"实体弹"假设固化进数据结构 —— 激光不产生子弹，只能返回空数组，属于模型不匹配而非参数差异。
- **一个发射器持有全部档位**：火力等级只是每次开火时读的一个数。
  若每档各建一个发射器对象，换级就等于换对象，会丢弃已积累的冷却，
  表现为"切火力时卡一下"，且来回切换时快慢不可预期。
- 升级解锁新形态（例如 lv3 出僚机）用发射器的 `minLevel` 钩子，不重建发射器集合。
- 选组合而非"每架一个 fire 函数"或"按武器类型分派"，是为了保留"主机 + 僚机 + 副武器 + BOSS 弹幕"
  复用同一条管线的能力 —— BOSS 弹幕只需一组发射器，不用复制一套逻辑。

## 四、资源：路径就近声明，启动期一次性加载

资源路径以静态字符串写进飞船文件的 `assetPaths`，
`ShipRegistry` 在 `GameEntry.start()` 里并发加载并缓存，之后业务层全部同步读取。

- 关键区分：**路径字符串是静态的**（可以写在飞船文件里）；
  **加载后的资源对象是运行时的**（必须异步加载并缓存）。因此缓存这一层不可省略。
- 加载完成后**先写缓存、再广播 `ship_assets_ready`**。顺序颠倒会让展示方读到空缓存。
- 展示方（选机界面）不在 `onLoad` 里盲目读缓存，而是等就绪事件补一次刷新 ——
  因为 `onLoad` 早于 `GameEntry.start()`。
- 多机型共用同一个子弹 prefab 时**路径统一指向 `common/`**，不各复制一份：
  同路径返回同一实例，复制只会产生多个对象池、降低命中率，且改结构要改多处。

## 五、子弹与对象池

- **prefab 由调用方注入**：`FireContext.bulletPrefab` → 发射器透传给 `spawnBullet`
  → `Bullet` 记住自己的 prefab → 回收时归还到对应的池。
  这样 `BulletManager` 退化为纯工厂，**不认识"机型"概念**，将来敌弹、僚机、多弹种都只是换一个 prefab。
- 激光机型的 `bulletPrefab` 为 `null`，`LaneEmitter` 早退并只告警一次（不每帧刷屏）。
- 对象池**按 prefab 分池**，避免不同弹种串味。
- **复用时必须完整复位**：`init()` 里取消残留回调、清零状态位、重设贴图与碰撞尺寸。
  漏了会出现"鬼影" —— 复用上一颗子弹的外观与残留行为。

## 六、数据与状态

- `PlayerData` 只存**本局会变**的值（`shipId` / `hp` / `weaponLevel` / `score`）。
- `maxHp` / `speed` / 外观一律现算。想加 buff 就加修饰量（`maxHpBonus` / `speedMultiplier`），
  不加基值副本 —— 副本就是第二份真源，改配置时必然漂移。
- 状态机只有四个状态，**PLAYING ↔ PAUSED 保留进度**，其余迁移清零。
  各组件只管自己"要不要继续推进"，不关心别人。

## 七、分层与依赖

- 依赖只能向上：L4 实体**不得运行时 import L5 管理器**，靠 `import type` 与 `init()` 注入解决。
- 分层判据是"**有没有行为**"而非"目录里有没有 `from 'cc'`"：
  要防的是"配置层偷偷做事情"，不是"配置层不认识引擎"。
- 跨模块通信走事件总线，组件之间互不直接持有引用。

## 八、后续工作的落位

| 要做什么 | 落在哪 | 是否碰核心逻辑 |
|---|---|---|
| 加一架飞机 | `ShipXxx.ts` + `ShipRegistry` 登记一行 + `resources/ships/<id>/` 放资源 | 否 |
| 加一种敌机 | `EnemyConfig` 加一行 | 否 |
| 加一个特效 | 做 prefab + 登记特效表 + 调用点播放 | 否 |
| 加一个升级项 | 乘区类走 `FireMods`；形态类走发射器的 `minLevel` | 否 |
| BOSS 弹幕 | 给 BOSS 挂一组发射器，复用同一条管线 | 否 |

## 九、待决策

1. **瓦片图集的存放位置**：`resources/Tiles` 与 `resources/Tilemap` 被 `MapManager` 静态引用，
   放在 `resources/` 下会无条件进包且不参与构建期裁剪。可移到 `assets/textures/`（小项目也可不动）。
2. **物理开关的落地方式**：2D 物理目前由编辑器工程设置开启，`GameEntry` 中对应代码行为注释状态，
   二者应统一。
3. **两份 Bullet_1 prefab**：`prefabs/entites/` 与 `resources/ships/*/` 各有一份，
   实际使用 `resources/common/bullet`，旧的需确认无引用后清理。
