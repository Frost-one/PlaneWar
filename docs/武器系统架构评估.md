# 武器系统抽离的架构评估

> 背景：仿《雷霆战机》的纵版射击。已实现武器升级（5 级），后续要做
> **飞船升级 + 多波次敌人 + BOSS**。
> 本文基于当前代码的实读（2026-09-17），回答三件事：抽离的理由、内联的代价、
> 以及面对这四项后续需求该怎么划边界。

---

## 一、先看清现状：一条 5 跳的射击管线

```
Player.update()                         ① 决定"何时开火"（受 input / state / shipId 影响）
   └─ weapon.update(dt, weaponId, level, x, y)
WeaponSystem.update()                   ② 计时 + 取缓存的 FirePlan
   └─ buildFirePlan(weaponId, level)
        ├─ getWeaponConfig(id)          ③ 查配置：levels[level - 1]
        └─ SHOT_BUILDERS[type](levelData) ④ 弹道几何：展开成 BulletSpawnParams[]
BulletManager.spawnBullet(x, y, shot)    ⑤ 实例化（每颗一次 instantiate）
   └─ Bullet.init() → applyVelocity() → RigidBody2D.linearVelocity
```

**实测出来的两个量级（决定后面所有性能讨论的量级感）：**

| 机型 / 等级 | 每轮弹数 × 每秒轮数 | ≈ 每秒生成（且之后销毁）的节点数 |
|---|---|---|
| 赤焰 散射 lv5（`count: 12, interval: 0.24`） | 12 × 4.17 | **≈ 50 个/秒** |
| 苍岩 贯穿 lv5（`count: 3, interval: 0.28`） | 3 × 3.57 | ≈ 11 个/秒 |

按 `BOUND_MAX_Y = 499`、子弹初速 1150 px/s 估算，单颗寿命约 0.8s
→ 赤焰满级时**同时在场约 40 颗子弹**，每颗都带 `RigidBody2D` + `Collider2D` + 一个 `Bullet` 组件。

## 二、Q1：为什么要从飞船文件里抽离出来？

四条理由，按"说服力"排序 —— **第 2 条是决定性的**。

### ① 职责分离：这两块东西的变更频率差一个数量级

- `Player.ts`（220 行）回答的是：**什么时候能动、能不能开火** —— 由 input、state、暂停语义决定。
- `WeaponSystem.ts` 回答的是：**这一轮发几颗、各偏多少度、间隔多久** —— 由策划数值决定。

一个版本里，Player 可能一次都不改；而弹道几乎每个版本都要调。
**把变更频率不同的东西放进同一个文件，等于让它们互相承担对方的回归风险。**

### ② ~~复用性：散射和贯穿今天已经在共用同一个函数了~~ ⚠️ 本条已撤回

> **2026-09-17 撤回**：这条是"现状描述"，不是"架构理由" —— 用它论证抽离等于用结果论证原因。
> 它只能证明"今天没重复"，证明不了"明天该抽离"。真正的需求推演见**第七节**。

```ts
const SHOT_BUILDERS: Record<WeaponType, ShotBuilder> = {
  [WeaponType.Spread]: buildLaneShots,   // ← 同一个函数
  [WeaponType.Pierce]: buildLaneShots,   // ← 同一个函数
  [WeaponType.Laser]:  buildLaserShots,
}
```

（保留下面的原始观察，仅作为事实记录，不再作为论据。）

两把武器的**排布规律完全一致**，差别只在 `count / spreadAngle / laneWidth` 三个数值。
内联到飞船文件里会发生什么：`ShipRed.ts` 里写一份展开，`ShipGreen.ts` 里再写一份**相同的**展开 ——
从 1 份变 N 份，而且 N 会随机型数线性增长。

### ③ 可测试性：`WeaponSystem.ts` 今天就是纯函数

它除了两个 `import type`（编译后消失）之外**不引用任何引擎类型**，
所以 `buildFirePlan('weapon_spread', 3)` 可以在任何环境下直接调用断言，不需要起 Cocos。
而 `Player` 是 `Component`，缠着 `input.on`、`EventBus`、节点生命周期 ——
把弹道写在里面，等于宣布"这段逻辑不可单测"。

### ④ 扩展成本：新加子弹属性的入口只有一个 —— `makeShot()`

```ts
function makeShot(levelData, angleDeg, offsetX = 0): BulletSpawnParams {
  return { angleDeg, offsetX, speed: ..., damage: ..., pierce: ... }
}
```

`damage` / `pierce` 就是这么加进去的 —— **改一处，所有武器同时生效**。
内联方案下每份重复代码都要改一遍，漏一份就是一个静默 Bug。

### 顺便：还有一条防 Bug 的语法级收益

`Record<WeaponType, ShotBuilder>` 有 **TS 穷尽性检查**：新加一个 `WeaponType` 而忘了注册 builder，
**编译期就报错**。换成写死在飞船里的 `switch`，漏一个分支是运行时行为（打不出子弹），
而且这类 Bug 在射击游戏里的表现是"没反应"，极难定位。

## 三、Q2：内联 vs 抽离，逐项权衡

| 维度 | 写在飞船文件内 | 抽离到 WeaponSystem |
|---|---|---|
| **耦合度** | 高：移动/输入/暂停语义 与 弹道几何 缠在一起，改数值要动 `Player` | 低：Player 只依赖一个 `update(...)` 调用 |
| **理解成本** | **低 ✅**：就近阅读，没有跳转 | **中 ❌**：要看 `update → buildFirePlan → SHOT_BUILDERS → buildLaneShots → makeShot` 四跳 |
| **调试成本** | 堆栈短，断点落一处 | 有 3 条 `return null` 的路径（武器不存在 / 等级越界 / 没 builder），排查要跨两个文件 —— **靠 `[WeaponSystem]` 前缀的 warn 兜底** |
| **多武器切换** | ❌ 每个飞船文件重写一遍逻辑；且 `level` 是该武器私有的索引（`levels[level-1]`），内联写法很容易退化成全局 `switch(level)`，**这正是"5 级散射切到激光"越界 Bug 的温床** | ✅ 切换只改 `weaponId` / `weapon` 对象；等级天然是武器私有的，跨武器不会串 |
| **武器升级（已实现）** | 每加一级都要动飞船代码 | 只在 `levels[]` 加一条；上限 = `levels.length` |
| **飞船升级（后续）** | 飞船文件会变成 `机型 × 等级` 的二维分支，真值容易在多份之间漂移 | 只产出**修饰量**，不改基础数值 |
| **BOSS 复用（后续）** | ❌ 复制一份逻辑给敌人用 | ✅ 纯函数层，敌我共用同一条管线 —— **见第五节，这条是决定性的** |
| **碰撞/渲染性能** | **完全相同（0 差异）** | **完全相同（0 差异）** |
| **每帧 CPU** | 少 1 次函数调用 | 多 1 次函数调用 + **每帧拼一次缓存 key 字符串**（详见第四节） |

**内联的真正优势只有一条，而且它是真的**：原型阶段就近阅读确实更快，
而且当两架飞机的行为**真的完全不同**时，通用化本身是要付出代价的。

但对本项目的判断是：**代价还没出现，收益已经兑现了** —— 因为 `buildLaneShots` 此刻正被两把武器共用。

### ⚠️ 一个必须在动手前纠正的直觉：**抽离 ≠ 有性能代价**

把每秒 50 次 `instantiate()` 和每秒 60 次函数跳转放在一起看，量级差了三到四个数量级：

| 开销来源 | 每帧/每秒次数 | 量级 |
|---|---|---|
| 抽象层：`weapon.update()` 一次调用 | 60/秒 | **纳秒级，可忽略** |
| 缓存 key：`\`${weaponId}#${weaponLevel}\`` 每帧拼一次字符串 | 60/秒 | **微秒级，很小但确实是浪费** |
| **无对象池**：`instantiate()` + `node.destroy()` | **50/秒（赤焰满级）** | **毫秒级 ⚠️ 真正的瓶颈** |
| **每颗子弹订阅 EventBus**：`onLoad` 里 `eventBus.on('state_change')`，`onDestroy` 里 off | 50 次订阅 + 50 次退订/秒 | **毫秒级 ⚠️** |
| `Vec2` 分配：`applyVelocity()` 里 `new Vec2(...)`，每颗子弹 init 和 onLoad 各一次 | 100+/秒 | GC 抖动 |

**结论：把武器逻辑内联回飞船，你几乎不会获得任何性能。
真正该动的是对象池和 EventBus 订阅方式 —— 那是另外三个独立的问题。**

## 四、顺手揪出来的三个现状问题（与"抽或不抽"无关，但更值钱）

| # | 位置 | 问题 | 影响 |
|---|---|---|---|
| 1 | `BulletManager.spawnBullet` | **没有对象池**：每发都 `instantiate`、每次回收都 `destroy`（注释里写着"后续接入对象池"，尚未做） | 满级 + BOSS 弹幕下是唯一的性能瓶颈 |
| 2 | `Bullet.onLoad` / `onDestroy` | **每颗子弹都订阅 `state_change`** | 实体从 40 涨到 BOSS 战的几百时，EventBus 上会有几百个 listener 反复增删。建议改为 `BulletManager` 订阅一次、遍历自己的 `bullets` 列表批量冻结 |
| 3 | `WeaponConfig.bulletPrefabIndex` vs `BulletManager` | 配置表说"对应 `@property([Prefab])` 数组的下标"，但 `BulletManager` **只有一个 `bulletPrefab` 字段** → 现在所有武器共用同一张子弹图，这个索引字段目前是死的 | 想让每把武器有不同的子弹外观，这一步必须补齐；否则多武器只是数值不同、看起来一样 |

## 五、Q3：结论 —— **保持抽离，但边界重划一层**

对"抽离 / 部分回收 / 重划"三个选项，明确的答案是：

> **不回收。保持抽离，并把边界从「飞船 ↔ 武器」改成「数据 ↔ 纯策略 ↔ 执行者」。**

### 边界重划（唯一需要动的地方）

```
┌ 数据层（唯一真值，扩张点）┐  WeaponConfig.levels[]   ← 加一级只需加一条数据
├──────────────────────────┤
├ 纯策略层（不 import cc） ─┤  WeaponSystem.buildFirePlan + SHOT_BUILDERS
│                          │  ⚠️ 敌我共用 —— BOSS 弹幕也挂在这里
├──────────────────────────┤
├ 持有/时机层              ┤  Player.weapon（timer、是否开火、能否开火）
├──────────────────────────┤
└ 执行层（对象池）         ┘  BulletManager → Bullet
```

**留在飞船文件里的**：`this.weapon` 这个持有关系 + 开火时机 + 暂停语义。
**不许进飞船文件的**：弹道几何、等级查表、升级曲线。

### 四个后续需求逐个落位

#### ① 武器升级（已实现）→ 保持现状，补两处安全带

- `weaponLevel` 必须 clamp 到 `[1, levels.length]`，避免"满级后再吃道具"索引越界。
- 激光 `levels` 是空数组，必须维持"先判空再索引"（现有 warn 是对的，别改成 `?? levels[0]`）。

#### ② 飞船升级 → **最容易骗你把逻辑搬回飞船的需求，但恰恰相反**

"飞船变强"听起来该写在飞船里 —— 但正确的处理是：**飞船升级只产出修饰量，不产出第二份数值。**

```ts
export interface FireMods {
  rateMultiplier: number      // 0.85 = 射速加快 15%
  damageMultiplier: number    // 1.2  = 伤害 +20%
  extraCount: number          // +1 = 每轮多发一颗
}

buildFirePlan(weapon: WeaponConfig, level: number, mods?: FireMods): FirePlan | null
```

理由是**组合爆炸**：3 机型 × 5 级飞船升级 × 5 级武器升级 = 75 种组合。
- 内联写法 → 75 份分支（O(n×m)）
- 修饰量写法 → 一张 mods 表 + 一条通用公式（O(n+m)）

这跟 `PlayerData` 里那条"基础属性 + 加成，绝不复制基值"是同一套路，别破例。

#### ③ 多波次敌人 → **与武器完全正交，别动武器模块**

需要的是 `WaveDirector`，而 `EnemyManager` 的注释里已经写了这个 TODO：

> *"出哪种、多常出"属于难度节奏，将来会整体搬去 WaveManager。*

建议：`EnemyManager` 退化为"按指令生成一架"的纯 spawner，`WaveDirector` 决定"第几波出什么"。
这和 `WeaponSystem`（几何）↔ `Player`（时机）的分工是同构的 —— **本项目其实已经有一致的解法了，照抄一遍即可。**

#### ④ BOSS → ⭐ 这是抽离方案最大的红利，也是最终的判断依据

雷霆战机类游戏的 BOSS 战，**80% 的内容就是弹幕**。BOSS 没有弹幕 ≈ BOSS 没做。

那么 BOSS 的弹幕要从哪来？两种结局：

| 方案 | BOSS 的下场 |
|---|---|
| 武器逻辑写在 `ShipRed.ts` 里 | BOSS 只能**复制一份**，从此两份并行维护 —— 玩家侧改一次，BOSS 不一定跟着改 |
| 武器逻辑是**不 import cc 的纯函数** | BOSS 直接调**同一个** `buildFirePlan`，只需把 `BulletManager` 换成敌弹版本（见下） |

**这就是判断依据：抽离的真正收益不是"玩家侧少改几行"，而是让"发射几何"成为一条中立管线，敌人能挂上去。**

给 BOSS 做时唯一要注意的一点：现在的 `BulletManager` 是**玩家的**（碰撞分组是"玩家子弹 vs 敌人"）。
BOSS 需要一个 `EnemyBulletManager`（或给现在的类加一个 `group` 参数），
**但它的上游 `buildFirePlan` 完全不用动** —— 这正是抽离兑现的方式。

### 什么条件下才该把逻辑回收进飞船文件？

给一个明确的判据，避免这条建议变成教条：

> **当出现"同类型武器、但排布规律不同"时——比如两架都用散射，但一架会追踪、一架不会——
> 那时加一个可选的钩子 `ShipConfig.overrideShots?: ShotBuilder`。**
> **钩子的"实现体"写在 `ShipRed.ts`（那才是它天然的家），但"调用点"仍然在 `WeaponSystem`。**

也就是说：**数据/策略流向是单向的，飞船永远是被查询方，不是执行方。**
只要守住这条，飞船文件里多写几个钩子也不会失控。

## 六、改动优先级（按"性价比"排序，与重构本身解耦）

| 优先级 | 项 | 理由 |
|---|---|---|
| **P0** | 打开物理系统 `GameEntry.ts:12` | 现在子弹和敌机都不动，其余讨论都是纸面 |
| **P1** | `BulletManager` 接入对象池 | 唯一的真瓶颈（50 节点/秒，BOSS 战会更高） |
| **P1** | 子弹暂停改由 `BulletManager` 统一处理，去掉每颗的 EventBus 订阅 | 实体数会随波次/BOSS 翻几倍 |
| **P2** | `getPlan` 缓存改成直接比两个变量，别每帧拼字符串 | 顺手，几乎零成本 |
| **P2** | 补齐 `bulletPrefab` 数组，让 `bulletPrefabIndex` 生效 | 否则多武器只是数值不同、外观一样 |
| **P3** | `buildFirePlan` 加 `FireMods` 参数 | 等飞船升级真开始做时再加，**不要提前** |

> P1/P2 无论你最终选"抽离"还是"内联"都该做 —— 它们是独立的性能债，
> 不该被卷进架构争论里。

## 七、重新评估：不看现状，只看需求（2026-09-17）

> 第二节的 ② 已撤回。这一节从头推演：**假设现在什么代码都没有**，
> 只知道要做"仿雷霆战机 + 武器升级 + 飞船升级 + 多波次 + BOSS"，该怎么划边界。

### 7.1 判据不是"有没有重复"，而是"什么东西会各自变化"

这类游戏的开火，实际有 **5 个变化轴**：

| # | 变化轴 | 例子 |
|---|---|---|
| 1 | 机型 | 散射 / 贯穿 / 激光 / 追踪 / 环形 |
| 2 | 火力等级（P 道具，局内） | lv1 单发 → lv5 十二发 |
| 3 | 飞船等级 / 改装（局外） | **不只是加数值，可能改变形态**：lv3 解锁僚机、lv5 变双束激光 |
| 4 | 叠加 | **主机弹道 + 僚机 + 副武器同时存在** |
| 5 | 敌我 | BOSS 弹幕 |

**轴 1、2 支持"每架飞船写自己的 fire 函数"；轴 3、4、5 不支持。**

其中**轴 4 是这类游戏的命门** —— 雷霆战机的装备体系本来就是
**主机 / 装甲 / 副武器 / 僚机** 分槽、且**可独立更换**的。
那么"一次开火"从来就不该是一段函数，而是**几个可自由组合的发射单元同时工作**。
一旦把主机+僚机+副武器硬编码进一个 `fire()`，你就失去了"换僚机不改主机"的能力。

### 7.2 三种组织方式对比

| | **A** 按武器类型分派（现状） | **B** 每飞船一个 `fire()` | **C** 发射器组合（建议） |
|---|---|---|---|
| 机型不同弹道 | ✅ 加一个 builder | ✅ 各写各的 | ✅ 装配不同 emitter |
| 形态随飞船等级变化 | ⚠️ 只能改数值 | ✅ 函数里加分支 | ✅ 换 emitters 列表 |
| **主机+僚机+副武器叠加** | ❌ | ❌ 全塞进一个函数 | ✅ 天然就是个列表 |
| **BOSS 复用** | ✅ | ❌ 复制一份 | ✅ |
| **激光（不同模型）** | ❌ 塞不进 `FirePlan` | ✅ | ✅ 独立 emitter |
| 扩展时要改中央文件吗 | 要 | 不用 | 不用 |
| 成本 | 低 | 最低 | 中 |

- **A 死于激光**：`FirePlan { interval, shots[] }` 把"实体弹"的假设固化进了数据结构，
  激光只能 `return []`（一个"什么都不做"的谎言）。要救它就得把 FirePlan 做成联合类型，
  于是入口签名被最复杂的那个分支污染。
- **B 死于叠加和 BOSS**：它就是为此刻的"一架飞机一条弹道"设计的，
  而你要做的四件事里有三件（僚机、改装改形态、BOSS）都在打破这个前提。

### 7.3 结论：抽离，但**抽离的单位要换**

不是"把整个 fire 抽到 WeaponSystem"，而是把抽离的粒度
从 **"整个开火函数"** 降到 **"一个发射器"**：

```ts
export interface FireContext {
  x: number
  y: number
  bullets: BulletManager      // 或敌弹版本
  mods: FireMods              // 飞船升级带来的修饰量
}

export interface Emitter {
  readonly id: string
  /** 到点了 —— 自己决定做什么（发实体弹 / 开激光 / 什么都不做） */
  fire(ctx: FireContext): void
  /** 持续型（激光）每帧推进判定；实体弹发射器不需要 */
  tick?(dt: number, ctx: FireContext): void
  onReset?(): void
}
```

**关键差异：Emitter 返回 `void`，而不是 `BulletSpawnParams[]`。**
"返回一发子弹的参数"这个契约本身就排除了激光；改成"你自己去执行"就什么都能装。

飞船文件从"逻辑容器"降为"装配清单"：

```ts
export const SHIP_BLUE: ShipConfig = {
  id: 'blue', name: '湛影',
  levels: [
    { emitters: [beamEmitter(BEAM_L1)] },                    // 飞船 lv1：单束
    { emitters: [beamEmitter(BEAM_L2)] },                    // lv2：加宽
    { emitters: [beamEmitter(BEAM_L3), wingmanLane(LANE_2)] }, // lv3：双束 + 僚机
  ],
}
```

  BeamEmitter.ts     激光（自己的模型 + 自己的 beamLevels 表）
  HomingEmitter.ts   将来
  WingmanEmitter.ts  僚机（可被任意机型装配）

### 7.4 激光写在哪（回答"完全不同时怎么办"）

1. 写在 **`entities/emitters/BeamEmitter.ts`** —— 不写进 ShipBlue.ts，也不塞进 `WeaponConfig.levels`。
2. 它有**自己的等级表** `beamLevels`（`width` / `tickInterval` / `length` / `damagePerTick`）。
   字段集与实体弹**不重叠**，硬塞进 `WeaponLevel` 只会造出一堆 0 占位 ——
   今天 `WEAPON_LASER.levels = []` 就是那个错误的症状，不是它的设计。
3. 它的判定不走 `Bullet`（没有飞行体、没有 RigidBody 弹道），走线段/矩形的持续检测。
   **这是模型差异，不是参数差异** —— 任何"用一份字段描述两种模型"的尝试都会失败。
4. `ShipBlue.ts` 里只剩一行装配。

### 7.5 什么时候才该把开火逻辑写进飞船文件

给明确判据，免得上面的建议变成教条：

> **可复用的几何 → `emitters/`（共享）；该机型独有的行为 → 允许写在 `ShipRed.ts`（钩子）。**
> 前提：钩子有名字、grep 得到、不阻塞别人。

满足任一即可下沉到飞船文件：
- 只会被这一架飞机用，且**确定不会**被 BOSS 用（例如赤焰的专属大招）
- 依赖飞船私有状态（例如"血量低于 30% 时弹道变形"）

反过来**必须留在 `emitters/`** 的：敌我共用的几何、需要被叠加的（僚机/副武器）、形态会随等级变化的。

### 7.6 迁移成本 & 一个诚实的退路

| 步 | 改动 | 风险 |
|---|---|---|
| 1 | `buildLaneShots` → `LaneEmitter`（返回数组改成内部调 `ctx.bullets.spawn`） | 小，纯搬 |
| 2 | `WeaponSystem` 从 `SHOT_BUILDERS[type]` 改为遍历 `emitters` | 中，Player 调用签名要变 |
| 3 | `ShipConfig` 加 `levels[].emitters`，`weaponId` 退役 | 中，配置表重构 |
| 4 | `BeamEmitter` + `beamLevels`（P3，配合激光一起做） | — |

> **诚实的退路**：如果你确定"永远 3 架飞机、没有僚机、BOSS 弹幕另写一套"，
> 那就直接选 **方案 B（每架一个 fire 函数写在 ShipRed/Green/Blue.ts）** ——
> 那也是个自洽的选择，只是届时要为 BOSS 和僚机各付一次代价。
> 选 C 的真正理由**不是**消除重复，而是**保住"组合"这个能力**。
