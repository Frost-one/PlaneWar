# 飞船模块重构设计

> 目标：**一架飞船 = 一个类（一个文件）**，其他所有文件（选机界面、Player、HUD）都从飞船定义里**取**数据，不再各自复制一份。
>
> 本文基于代码实际内容 + 编辑器实际接线核对得出。核对时间：2026-09-17

---

## 〇、先说结论（TL;DR）

你的五层方案**方向是对的**，但有三处要修：

| # | 你的方案 | 修正 |
|---|---|---|
| 1 | ①→②→③→④→⑤ 是一条链，④ 在 ③ 下游 | **④ 不是链条的一环，是与 ①②③ 平行的第二条输入**。配置链管"是什么"，资源桥管"长什么样"，两者在装配层合流 |
| 2 | 契约层放 `spriteIndex: number` | **契约层里一个资源字段都不该有**。机型↔外观的对应关系整个下沉到 ④，用 `id` 做键 |
| 3 | ⑤「装配」只写了 `Player 节点 + applyShip()` | **缺了"运行时状态层"**。必须把"配置模板（不可变）"和"本局实例（可变）"分开，否则 applyShip 该写什么没有判据 |

另外补一条你没提但最关键的约束：

> **两条硬约束逼出了整个架构** —— ① `assets/res` 不是 Bundle，运行时不能按路径加载；② `Player` 是 prefab 实例，**prefab 里的 `@property` 不能引用场景节点/组件**。
>
> 所以 ④ 资源层的形态是**唯一解**：`组件（编辑器拖图）+ 单例注册表（跨墙查询）` 两件套。你图里 `④ → Player` 那条直连箭头，在 Cocos 里画不出来。

## 一、现状核对（我实际查到的）

先摆事实，避免在错误前提上设计。

| 位置 | 实际接线 |
|---|---|
| `Player.prefab` | Sprite 挂的是 **`ship_0009.png`** —— 既不是赤焰也不是任何一架可选机；`weaponId` 硬编码 `"weapon_spread"`；`shipSpriteList` 是**空数组** |
| `Game.scene` 的 `Player` 实例 | 只覆盖了 `bulletManager` 引用；另外**多挂了 3 个空的 `BulletManager` 组件**（疑似误操作残留） |
| `Menu.prefab` 的 `ShipSelectView` | `shipSprites` 已正确拖入 `ship_0000 / 0001 / 0002`，预览图 + 两个标签 + 左右箭头都接好了 |
| `GameHUD` | 只显示分数 / 生命 / 火力，**不显示机型** |

### 由此得到一个重要结论

**换皮从来没生效过。** 菜单里预览图在变、文字在变，但场景里的飞机永远是 `ship_0009` 那张 ——
因为 `Player.onPlayerDataChange` 是个**空方法**（只 `getShipConfig` 拿了个 cfg 就 return 了），
而 `Player.shipSpriteList` 又是空的。

同时 `PlayerData.applyShip()` 里事件名**拼错了**：

```ts
eventBus.emit('play_data_change', this.getSnapshot())   // ← 少了个 "er"
```

它广播的是 `play_data_change`，而所有订阅者听的是 `player_data_change`。
所以点箭头换机型，**全工程只有 ShipSelectView 自己的显示更新了**（它是被动读快照的），
HUD 和 Player 一个都没收到。

顺手记三个同类问题：
- `PlayerData.attack` 是**死字段**（全工程无人读写，只有 PlayerData 自己内部传来传去）
- `PlayerData.fromJSON` 里 `shipId: this.shipId ?? DEFAULT_SHIP_ID` 写错了，应该是 `data.shipId`
- `Player.onDestroy` 只退订了 `state_change`，漏了 `player_data_change`

## 二、修正后的分层

左侧是**配置链**（纯数据，禁止 import cc），右侧是**资源桥**（唯一允许碰 `SpriteFrame` 的地方），
两者平行，在底部的运行时/使用方合流。

```
配置链 · 纯数据                        资源桥 · 唯一允许 import SpriteFrame
─────────────────                     ──────────────────────────────
① ShipConfig.ts       契约 · interface    ④ ShipAssetTable.ts  组件 · 拖 3 张图
        ↓                                          ↓ bind(Map)
② ShipRed/Green/Blue   数据                ④ ShipAssets.ts      单例查询入口
        ↓
③ ShipTable.ts         汇总 · 全表 + 查表
        └──────────────┬───────────────────────────┘
                       ↓
              ⑤ PlayerData   运行时状态（本局会变的值）
                       ↓
        ⑥ Player（读 cfg 现算外观/武器/速度） · ⑥ ShipSelectView（只改 shipId）
```

### 六层职责表

| 层 | 文件 | 层级别 | 规则 |
|---|---|---|---|
| ① 契约 | `data/ships/ShipConfig.ts` | L0 | 只有 `interface`。**不含任何资源字段** |
| ② 数据 | `data/ships/ShipRed.ts` 等 3 个 | L0 | 一架一个文件，纯数值 + 强引用武器 |
| ③ 汇总 | `data/ships/ShipTable.ts` | L0 | `SHIP_TABLE[]` + 查表 + 循环切换 |
| ④ 资源 | `managers/ShipAssetTable.ts`（组件） | L5 | 拖图，`onLoad` 灌进注册表 |
| ④ 资源 | `core/ShipAssets.ts`（单例） | L1 | 查询入口，**所有使用方只认它** |
| ⑤ 运行时 | `data/PlayerData.ts` | L2 | 只存本局会变的值；派生值现算 |
| ⑥ 使用方 | `entities/Player.ts`、`ui/ShipSelectView.ts` | L4/L6 | 不复制数据，只引用 |

> **为什么注册表放 `core/`（L1）而不是跟组件一起放 `managers/`（L5）？**
> `Player` 属于 L4，按项目的分层规矩**只允许依赖 L0~L2**。如果注册表挂在 L5 的文件里，
> `Player` 一 import 就破坏了"L4 不许运行时 import L5"。放 L1 才守得住规矩。
> 这个理由和 `EventBus` 能放 L1、而 `UIManager` 只能放 L5 是同一个道理。

## 三、逐文件设计

### ① `data/ships/ShipConfig.ts` —— 契约层

```ts
import type { WeaponConfig } from '../config/WeaponConfig'

/**
 * 机型契约 —— 定义"一架飞机必须有什么"。
 * ⚠️ L0 纯数据层：禁止 import cc，禁止出现任何资源字段（SpriteFrame / Prefab / 下标）。
 *    机型 ↔ 外观 的对应关系整个下沉到资源层（ShipAssetTable），用 id 做键。
 */
export interface ShipConfig {
  readonly id: string
  readonly name: string
  readonly maxHp: number
  /** 移动速度（px/s，设计单位） */
  readonly speed: number
  /**
   * 主武器：直接持有配置对象（强引用），不用 `weaponId` 字符串。
   * 弱引用打错字不报错、只在运行时 warn；强引用编译期就挂。
   * 与 WeaponConfig 的 1:1 关系由数据本身保证，不再靠注释约定。
   */
  readonly weapon: WeaponConfig
  /** 选机界面的一句话定位（可选，纯展示） */
  readonly tagline?: string
}
```

**关于 `spriteIndex` 为什么直接删掉、而不是换成 `spriteKey`：**

`ShipConfig.ts` 原来的注释写的是"用下标而不是资源路径，将来改造成 Bundle 后可换成 spritePath"——
思路对，但**下标本身就是隐患**：数组拖错一位不报错，只是悄悄换成另一架飞机的图。

我先考虑过换成 `spriteKey: 'ship_red'` 这种稳定字符串键。但仔细一想：
**每架飞机只有一个 key、且它必然等于 `id`**，那这个字段就是纯冗余。
所以最终方案是 **契约层彻底不出现资源字段**，对应关系全部由 ④ 用 `id` 建表。
将来真需要多套皮肤（原神那种），再加 `skins` 表也不迟 —— 现在加就是过度设计。

```ts
/** 赤焰（红）：散射 · 中血中速，清杂兵 */

  id: 'ship_red',

```

`ShipGreen.ts` / `ShipBlue.ts` 同构（苍岩 → `WEAPON_PIERCE`，湛影 → `WEAPON_LASER`）。

> **值不值得为 3 架飞机拆 3 个文件？**
> 值得。判据不是"现在有多少代码"，而是"以后会不会各自长东西"。
> 你参考的 MOBA / 原神设计里，**一个英雄一个文件**的意义在于：技能、被动、专属机制都住在同一个文件里，
> 想改某个角色一眼就能找到。本项目下一步必然要做"每架飞机的专属机制"，
> 现在拆好，`ShipRed.ts` 就是它天然的家；不拆，将来还得再搬一次。
>
> 单文件只有 10 行不丢人 —— **文件结构是按未来的扩展点切的，不是按当前行数切的。**

### ③ `data/ships/ShipTable.ts` —— 汇总层

```ts
import type { ShipConfig } from './ShipConfig'
import { SHIP_RED } from './ShipRed'
import { SHIP_GREEN } from './ShipGreen'
import { SHIP_BLUE } from './ShipBlue'

/**
 * 全工程唯一的"机型全表 + 按 id 查询"入口。
 *
 * 【为什么它必须独立成文件，不能合并回 ShipConfig.ts】
 *   它要 value-import 三个机型文件；而那三个文件又要 import type ShipConfig。
 *   合并就等于让契约层反向依赖数据层 —— 虽然 `import type` 编译后消失、跑得起来，
 *   但只要有人把 `import { ShipConfig }` 写成值引用，立刻就成循环依赖。
 *   拆开的好处是：**ShipConfig.ts 变成一个没有任何运行时代码的纯类型文件，循环在结构上不可能发生。**
 *
 * 【为什么不叫 ShipDefs / ShipConfigs / ShipRegistry】见第十二节。
 */
export const SHIP_TABLE: readonly ShipConfig[] = [SHIP_RED, SHIP_GREEN, SHIP_BLUE]

export const DEFAULT_SHIP_ID = SHIP_RED.id

/** 允许从 id 列表反查，供存档校验 / Debug 面板使用 */
export const SHIP_IDS: readonly string[] = SHIP_TABLE.map((c) => c.id)

/** 按 id 查机型，查不到返回 null（调用方自行决定兜底） */
export function getShip(id: string): ShipConfig | null {
  return SHIP_TABLE.find((c) => c.id === id) ?? null
}

/** 兜底版：查不到时回落默认机型。UI 用这个，省得到处写 `?? SHIP_TABLE[0]` */
export function getShipOr(id: string): ShipConfig {
  return getShip(id) ?? SHIP_RED
}

/**
 * 循环取"第 offset 架"（选机界面左右箭头用）。
 * 把取模逻辑收在这里，是因为 JS 的 % 对负数返回负值（-1 % 3 === -1，不是 2），
 * 必须 `((x % n) + n) % n` 才对 —— 这种坑不该让 UI 层记。
 */
export function cycleShip(currentId: string, offset: number): ShipConfig {
  const total = SHIP_TABLE.length
  const current = SHIP_TABLE.findIndex((c) => c.id === currentId)
  const base = current < 0 ? 0 : current
  return SHIP_TABLE[(((base + offset) % total) + total) % total]
}
```

### ④-a `core/ShipAssets.ts` —— 注册表（查询入口，L1）

```ts
import type { SpriteFrame } from 'cc'

/**
 * 机型外观注册表 —— 全工程唯一"机型 id → 外观图"的查表入口。
 *
 * 【为什么要单例注册表，而不是直接持有 ShipAssetTable 组件引用】
 *   Player 是 prefab 实例，而 prefab 里的 @property【不能引用场景节点/组件】，
 *   所以 Player 根本拿不到场景里那个 ShipAssetTable。只能由它主动把表灌进来。
 *
 * 【为什么放 core/（L1）】
 *   Player 属 L4，只允许依赖 L0~L2。放这里才不破坏分层。
 *   （import type 编译后消失，本文件运行时不依赖 cc）
 */
class ShipAssetRegistry {
  private map: Map<string, SpriteFrame> | null = null

  /** 由 ShipAssetTable 在 onLoad 时调用 */
  public bind(map: Map<string, SpriteFrame>): void {
    this.map = map
  }

  /** 取外观图；未注册或漏拖图时返回 null —— 调用方保持原样，绝不静默换错图 */
  public get(id: string): SpriteFrame | null {
    return this.map?.get(id) ?? null
  }
}

export const shipAssets = new ShipAssetRegistry()
```

### ④-b `managers/ShipAssetTable.ts` —— 资源组件（L5）

```ts
import { _decorator, Component, SpriteFrame } from 'cc'
import { SHIP_TABLE } from '../data/ships/ShipTable'
import { SHIP_RED } from '../data/ships/ShipRed'
import { SHIP_GREEN } from '../data/ships/ShipGreen'
import { SHIP_BLUE } from '../data/ships/ShipBlue'
import { shipAssets } from '../core/ShipAssets'
const { ccclass, property } = _decorator

/**
 * 资源层 —— 飞船模块里【唯一】允许 import SpriteFrame 的文件（"资源墙"）。
 *
 * 【形态为什么是"组件 + 注册表"两件套】
 *   硬约束 1：assets/res 不是 Bundle → 运行时不能按路径加载，只能编辑器拖引用
 *   硬约束 2：Player 是 prefab → prefab 内 @property 不能引用场景组件
 *   ⇒ 只能由"场景里的组件把图收起来"，再通过单例注册表让 prefab 里的组件查到。
 *
 * 【为什么每架一个具名字段，而不是一个 SpriteFrame 数组】
 *   数组靠"下标对齐"建立契约，拖错一位不报错、只是悄悄换成别的飞机的图。
 *   具名字段把"这架用哪张图"写在字段名里 —— 对不上就是编译不过 / 一眼看出来。
 *
 * 上限：机型数 < 10 时这个写法最省心。再多就该把图挪进 resources Bundle，
 *      改用 ShipConfig.spritePath: string 走路径加载（原注释里的那个方向）。
 */
@ccclass('ShipAssetTable')
export class ShipAssetTable extends Component {
  @property({ type: SpriteFrame, tooltip: '赤焰（ship_0000）' })
  redSprite: SpriteFrame | null = null

  @property({ type: SpriteFrame, tooltip: '苍岩（ship_0001）' })
  greenSprite: SpriteFrame | null = null

  @property({ type: SpriteFrame, tooltip: '湛影（ship_0002）' })
  blueSprite: SpriteFrame | null = null

  protected onLoad(): void {
    const pairs: [string, SpriteFrame | null][] = [
      [SHIP_RED.id, this.redSprite],
      [SHIP_GREEN.id, this.greenSprite],
      [SHIP_BLUE.id, this.blueSprite],
    ]

    const map = new Map<string, SpriteFrame>()
    for (const [id, frame] of pairs) {
      if (frame) map.set(id, frame)
    }

    // 缺图当场喊出来 —— 否则运行时表现是"切机型没反应"，极难排查
    for (const cfg of SHIP_TABLE) {
      if (!map.has(cfg.id)) {
        console.warn(`[ShipAssetTable] 机型 ${cfg.id}（${cfg.name}）没有拖外观图，外观不会切换`)
      }
    }

    shipAssets.bind(map)
  }
}
```

### ⑤ `data/PlayerData.ts` —— 运行时状态层

这一层是**你的方案里缺的那一层**，也是 applyShip 判据的来源。

```ts
import { eventBus } from '../core/EventBus'
import type { ShipConfig } from './ships/ShipConfig'
import { DEFAULT_SHIP_ID, getShipOr } from './ships/ShipTable'

/**
 * 玩家运行时数据的形状。
 * ⚠️ 只放【本局会变】的值；能从 shipId 现算的一律带 `派生` 标记，不作为字段存储。
 */
export interface IPlayerData {
  shipId: string
  weaponLevel: number
  hp: number
  score: number
  /** 派生：当前机型血上限（取快照时现算，不可能与配置表漂移） */
  maxHp: number
  /** 派生：当前机型移速 */
  speed: number
}

export class PlayerData {
  private shipId: string = DEFAULT_SHIP_ID
  private weaponLevel: number = 1
  /** 当前血量；血上限由机型现算，不存 */
  private hp: number = getShipOr(DEFAULT_SHIP_ID).maxHp
  private score: number = 0

  /** 当前机型；查不到时回落默认机型，保证 .maxHp / .speed 一定拿得到 */
  public getShip(): ShipConfig {
    return getShipOr(this.shipId)
  }

  public getSnapshot(): Readonly<IPlayerData> {
    const cfg = this.getShip()
    return {
      shipId: cfg.id,
      weaponLevel: this.weaponLevel,
      hp: this.hp,
      score: this.score,
      maxHp: cfg.maxHp, // 派生
      speed: cfg.speed, // 派生
    }
  }

  public addScore(n: number): void {
    this.score += n
    this.emit()
  }

  /** 承受伤害：下限 0，改完广播 */
  public takeDamage(n: number): void {
    this.hp = Math.max(0, this.hp - n)
    this.emit()
  }

  public isDead(): boolean {
    return this.hp <= 0
  }

  /** 新开一局：按当前机型把运行时状态复位 */
  public reset(): void {
    this.hp = this.getShip().maxHp
    this.weaponLevel = 1
    this.score = 0
    this.emit()
  }

  /**
   * 换机型 —— 【唯一】的"按模板装配实例"的动作。
   *
   * 只写"跟机型绑定、且本局会变"的值：当前血量 + 火力等级。
   * 血上限 / 移速 / 武器 / 外观 全是派生的，一律现算，不在这里复制 ——
   * 复制就是第二份真值，改配置时必然漂移。
   *
   * ⚠️ 火力等级必须归 1：等级索引的是【武器自己的弹道表】(WeaponConfig.levels[level-1])。
   *    从 5 级散射切到激光还留着 5 级，等于拿别的武器的等级去索引本武器的表 —— 直接越界。
   */
  public applyShip(cfg: ShipConfig): void {
    this.shipId = cfg.id
    this.hp = cfg.maxHp
    this.weaponLevel = 1
    this.emit()
  }

  /** 批量、部分修改【可变的】运行时字段（shipId 不在其中：换机型必须走 applyShip，否则血量/等级会不同步） */
  public setPlayerData(data: Partial<Pick<IPlayerData, 'weaponLevel' | 'hp' | 'score'>>): void {
    if (data.weaponLevel !== undefined) this.weaponLevel = data.weaponLevel
    if (data.hp !== undefined) this.hp = data.hp
    if (data.score !== undefined) this.score = data.score
    this.emit()
  }

  /** 存档：只序列化真字段，派生字段不落盘（读档时由机型算出来） */
  public toJSON(): object {
    return {
      shipId: this.shipId,
      weaponLevel: this.weaponLevel,
      hp: this.hp,
      score: this.score,
    }
  }

  public fromJSON(data: any): void {
    this.shipId = typeof data?.shipId === 'string' ? data.shipId : DEFAULT_SHIP_ID
    this.weaponLevel = data?.weaponLevel ?? 1
    this.hp = data?.hp ?? this.getShip().maxHp
    this.score = data?.score ?? 0
    this.emit()
  }

  /** 唯一的广播出口，顺便把之前拼错的事件名 `play_data_change` 修掉 */
  private emit(): void {
    eventBus.emit('player_data_change', this.getSnapshot())
  }
}

export const playerData = new PlayerData()
```

**"存储 vs 派生"这条线的判据（很重要，是这层存在的全部意义）：**

| 值 | 存 / 派生 | 理由 |
|---|---|---|
| `shipId` | **存** | 玩家选择，会变 |
| `hp` | **存** | 局内被打会变 |
| `weaponLevel` | **存** | 吃 P 道具会变 |
| `score` | **存** | 局内会变 |
| `maxHp` | 派生 | 只跟机型有关，静态 → 存副本必然漂移 |
| `speed` | 派生 | 同上 |
| `weapon` | 派生 | 由 shipId 决定 |
| 外观图 | 派生 | 由 shipId 决定 |
| ~~`attack`~~ | **删** | 死字段，全工程无人读写 |

> 将来加 buff 系统怎么办？加的是**修饰量**（`maxHpBonus` / `speedMultiplier`），
> 而不是把基值复制一份进来 —— 这正是 MOBA 里"基础属性 + 加成"的标准做法。

### ⑥ 使用方之一：`entities/Player.ts`

改动点：
- **删** `@property weaponId`（改从 `cfg.weapon` 取）
- **删** `@property shipSpriteList`（改从 `shipAssets` 取）
- `onPlayerDataChange` 补全实现：把 cfg 缓存下来 + 换外观
- `onDestroy` 补上漏掉的 `player_data_change` 退订

```ts
import { _decorator, Component, EventKeyboard, Input, input, KeyCode, Sprite } from 'cc'
import { eventBus } from '../core/EventBus'
import { StateChangePayload, GameState } from '../data/GameState'
import { BulletManager } from '../managers/BulletManager'
import { shipAssets } from '../core/ShipAssets'
import { getShipOr } from '../data/ships/ShipTable'
import type { ShipConfig } from '../data/ships/ShipConfig'
import { IPlayerData, playerData } from '../data/PlayerData'
import { WeaponSystem } from './WeaponSystem'
const { ccclass, property } = _decorator

@ccclass('Player')
export class Player extends Component {
  private keyLeft = false
  private keyRight = false
  private keyUp = false
  private keyDown = false
  private isPaused = true

  @property(BulletManager)
  bulletManager: BulletManager | null = null

  /** 当前机型配置。缓存下来，避免 update 每帧查表 */
  private ship: ShipConfig = getShipOr(playerData.getSnapshot().shipId)

  private readonly weapon = new WeaponSystem()

  protected onLoad(): void {
    input.on(Input.EventType.KEY_DOWN, this.onKeyDown, this)
    input.on(Input.EventType.KEY_UP, this.onKeyUp, this)

    this.weapon.bind(this.bulletManager)

    eventBus.on('state_change', this.onStateChange, this)
    eventBus.on('player_data_change', this.onPlayerDataChange, this)

    // 首次进入主动拉一次：把 prefab 里那张占位图换成当前机型的外观
    this.onPlayerDataChange(playerData.getSnapshot())
  }

  protected onDestroy(): void {
    input.off(Input.EventType.KEY_DOWN, this.onKeyDown, this)
    input.off(Input.EventType.KEY_UP, this.onKeyUp, this)
    eventBus.off('state_change', this.onStateChange, this)
    eventBus.off('player_data_change', this.onPlayerDataChange, this)  // ← 原来漏了
  }

  /**
   * 玩家数据变化：同步机型和外观。
   * 数值（血上限 / 移速）不在这里存 —— update 直接从 cfg 读，单一数据源。
   */
  private onPlayerDataChange(data: Readonly<IPlayerData>): void {
    const cfg = getShipOr(data.shipId)
    const changed = cfg.id !== this.ship.id
    this.ship = cfg
    if (changed) this.applyShipVisual(cfg)
  }

  /** 换机型外观：图从资源注册表取；取不到就保持原样（绝不静默换错图） */
  private applyShipVisual(cfg: ShipConfig): void {
    const frame = shipAssets.get(cfg.id)
    if (!frame) {
      console.warn(`[Player] 机型 ${cfg.id}（${cfg.name}）没有外观图，本机外观不切换`)
      return
    }
    const sprite = this.getComponent(Sprite)
    if (sprite) sprite.spriteFrame = frame
  }

  private updateMove(deltaTime: number): void {
    let dirX = (this.keyRight ? 1 : 0) - (this.keyLeft ? 1 : 0)
    let dirY = (this.keyUp ? 1 : 0) - (this.keyDown ? 1 : 0)
    if (dirX === 0 && dirY === 0) return

    const len = Math.sqrt(dirX * dirX + dirY * dirY)
    dirX /= len
    dirY /= len

    const p = this.node.position
    const speed = this.ship.speed            // ← 原来读 playerData 里的副本，现在读配置
    let newX = p.x + dirX * speed * deltaTime
    let newY = p.y + dirY * speed * deltaTime

    newX = Math.max(GameConfig.BOUND_MIN_X, Math.min(GameConfig.BOUND_MAX_X, newX))
    newY = Math.max(GameConfig.BOUND_MIN_Y, Math.min(GameConfig.BOUND_MAX_Y, newY))
    this.node.setPosition(newX, newY)
  }

  protected update(deltaTime: number): void {
    if (this.isPaused) return
    this.updateMove(deltaTime)

    const p = this.node.position
    this.weapon.update(
      deltaTime,
      this.ship.weapon,                     // ← 强引用，不再传 weaponId 字符串
      playerData.getSnapshot().weaponLevel,
      p.x,
      p.y + GameConfig.BULLET_SPAWN_OFFSET_Y,
    )
  }

  // onKeyDown / onKeyUp / handleDebugKey / onStateChange 保持原样
}
```

> ⚠️ `applyShipVisual` 只在 `changed` 时才换图 —— 否则每次 `addScore` 触发的广播都会重设一次
> `spriteFrame`，白白打断合批。这是"订阅广播"写法里最常见的性能坑。

## 四、行为层（你 image#1 的第 ④ 层）放哪？

**结论：留在 `WeaponSystem.SHOT_BUILDERS`，不要搬进飞船文件。**

理由：现在 **3 把武器 = 3 个 `WeaponType`**，`Record<WeaponType, ShotBuilder>` 这张分派表
本身就有 TS 穷尽检查（漏一个类型直接编译报错），而且散射和贯穿的排布规律完全一致、可以共用同一个 builder。
搬进飞船文件反而会让两架飞机的相同逻辑重复两份。

**什么时候该搬？** 出现"**同类型武器、不同行为**"的时候 ——
比如将来有两架飞机都用散射，但一架的子弹会追踪敌人、一架不会。
那时在 `ShipConfig` 加一个可选钩子，而它天然的家就是 `ShipRed.ts`：

```ts
export interface ShipConfig {
  // ...
  /** 可选：该机型对武器行为的覆盖（不写就用 SHOT_BUILDERS 的默认行为） */
  readonly overrideShots?: ShotBuilder
}
```

这正是 MOBA 里"英雄专属技能"的位置 —— 现在还没有专属机制，所以先不加。
**扩展点留在注释里，不留在代码里**，避免为了想象中的需求提前抽象。

## 五、三条铁律（让设计自我约束）

1. **`data/ships/**` 里出现【行为】就是错误。**（2026-09-17 改判据）
   原来的表述是"出现 `from 'cc'` 就是错误"，但**目录不是判据，有没有行为才是**：
   - 有状态 / 有副作用 / 需要引擎对象 → 是行为，不许进 `data/`（`BeamEmitter` 属于这类）
   - 纯数值 / 纯声明 → 是数据，**即使它需要 import cc 也照进不误**
     （例如将来的资源索引表 `ShipAssetTable`，它 import SpriteFrame 但只是张表）
   这么改是为了让规则服务于"健壮"而不是反过来：
   我们真正要防的是"配置层偷偷做事情"，不是"配置层不认识引擎"。
2. **只有 `ShipAssetTable.ts` 和 `core/ShipAssets.ts` 认识 `SpriteFrame`。** 其他文件一律通过 `shipAssets.get(id)` 拿图。
3. **能从 `shipId` 现算的值，禁止在 `PlayerData` 里存第二份。** 想加 buff 就加修饰量，不要加基值副本。

这三条是**可检查的**（第 1、2 条用 grep 就能查），比"注意分层"这种口号有用得多。

## 十、资源加载：`res` 要不要改名为 `resources`？（2026-09-17 补充）

### 结论：**不要改。**继续保持 `res`，理由不是习惯，是包体。

#### 先说一个被忽略的事实：改名不需要动任何引用

对本仓库做过一次全量扫描（`assets` 下 501 个资源、所有 prefab/scene/ts）：

| 项 | 结果 |
|---|---|
| 代码里用**路径字符串**加载资源的地方（`resources.load` / `assetManager.load*`） | **0 处** |
| 引用方式 | 全部是 `__uuid__`（`db://` 资产引用），写在 **6 个序列化文件**里 |
| `scenes/Game.scene` | 28 条（其中 20 条是 `MapManager` 的瓦片数组） |
| `prefabs/ui/Menu.prefab` | 3 条（`ship_0000/0001/0002`） |
| `prefabs/entites/Player.prefab` | 1 条（`ship_0009`） |
| `prefabs/entites/Enemy_{Normal,Elite,Boss}.prefab` + `Bullet_1.prefab` | 各 1 条 |
| 被引用的**不同**资源 | 36 个（res 下仅 27 个：7 张飞机 + 20 张瓦片） |

**引用靠 uuid，不靠路径。** 所以 `res → resources` 的改名，代码和 prefab **一行都不用改**。

> 顺带一个结论：`res` 下绝大多数资源（120 张瓦片里的 100 张、4 张 Tilemap 图集）
> **从来没被任何东西引用过**。这个数字后面会用到。

#### 三条可选路径，按推荐度排

| 方案 | 做法 | 代价 |
|---|---|---|
| **A（推荐）** 保持 `res`，需要时把**子目录**勾 Bundle | 选中文件夹 → 属性检查器勾「配置为 Bundle」（3.8 起也可在 项目设置 → Bundle 配置）→ `assetManager.loadBundle('ships')` | 零改动，随时可逆 |
| B 改名 `resources`（内置 Bundle） | `resources.load('Ships/ship_0000/spriteFrame', SpriteFrame, cb)` | 官方原文：**resources 内所有资源都会被无条件导出**，无用资源无法自动剔除，`config.json` 变大、JSON 自动合并策略受影响 |
| C 什么都不做 | 继续 `@property` 拖拽 | 机型变多时接线成本高 |

**方案 B 在你这个项目上的实际代价**：150 张图里只有 27 张被引用，剩下 120+ 张会全部无条件进包。
这不是理论风险 —— 上面那张扫描表就是证据。

#### 选 A 时的两个坑（官方文档明确写了）

1. **别把整个 `res` 做成 Bundle，只对子目录做。**
   官方 FAQ 原文：Bundle 里放的所有资源都会被打包出来，图集尤其会造成包体膨胀
   （因为图集本身、图集大图、图集内小图都可能被判定为需要导出）。
   `res` 下正好有 4 张 Tilemap 图集 + 120 张瓦片。
   ⇒ 正确做法是只把将来真正要动态加载的那一小撮放进 `res/ships/`（Bundle），
   瓦片和地图图集留在主包里走 `@property`（它们本来就被 `MapManager` 静态引用）。
   Bundle **不支持嵌套**，所以不能 `res` 和 `res/ships` 同时是 Bundle —— 只能选后者。

2. **一份资源不要同时走"静态引用"和"动态加载"。**
   官方规则：同一资源被多个 Bundle 引用时，优先级**不同**则归高优先级、低优先级只存引用记录；
   优先级**相同**则**每个 Bundle 各复制一份**。
   ⇒ 如果某天把 `res/Ships` 做成 Bundle，而 `Menu.prefab`（主包）又在拖 `ship_0000`，
   一旦优先级没设对，这张图就会打进包里**两份**。
   ⇒ 约定：**一个资源要么静态拖引用、要么动态加载，不许两边占。**

#### 如果哪天真要改名，操作清单

1. **在编辑器的资源管理器里右键重命名**（不要在 Windows 资源管理器里改）—— 由 Cocos 自己维护 `.meta` 与引用。
2. `assets/res.meta` **必须跟着改成 `resources.meta`**。
   （你项目里 `scripts/`、`scenes/`、`prefabs/`、`res/` 四个目录都各自有 `.meta`，别漏。）
   漏了会给这个目录生成新 uuid —— 目录 uuid 目前**没有**被任何地方引用，所以不会断引用，但会触发一次全量重导入。
3. `library/` 是按 uuid 缓存的产物，**不用手动改**，重开编辑器自愈，等一次导入即可。

## 十一、命名：`ShipTable` / `ShipAssetTable` 是通行写法吗？

### 结论：能用，但它们来自**两条不同的血脉**，混在一起会误导人

| 名字 | 真正出处 | 它原本的语义 |
|---|---|---|
| `Def(s)` | RimWorld 的 Def 系统（`ThingDef` + `DefDatabase<T>`） | *"Def 是菜谱，不是菜"* —— 强调**静态定义 vs 运行时实例**。同族还有 Factorio 的 prototype |
| `Catalog` | Unity Addressables 的 **content catalog** | 是"资源的**索引/地图**"（key → 物理位置），而且是**构建自动生成的 JSON**，不是手写的表 |

⇒ `Catalog` 这个词在业界默认是"**可寻址资源的运行时索引**"，
用在你这里那张编辑器手拖的 `@property` 表上算借用，别人会误以为你做了动态加载。
**语义错位比名字难听严重得多。**

### 业界常见后缀谱系

| 层 | 常见叫法（按流行度） | 语境 |
|---|---|---|
| 静态定义 | `Config` / `Cfg` > `_def` > `Template` > `Data` / `DataAsset` > `Blueprint` > `Spec` > `Prototype` | `Config` 是国内策划配表语境的绝对主流；`DataAsset`/`DataTable` 是 UE；`<X>SO` 是 Unity ScriptableObject 的书写习惯 |
| 运行时实例 | `Data` > `State` > `Runtime` > `Instance` > `Context` | Unity 官方建议给 SO 加 `Data`/`SO` 后缀区分 MonoBehaviour |
| 资源引用表 | `Assets` > `AssetTable` > `AssetMap` > `Res` > `SkinTable` > `SpriteTable` | 皮肤系统里通常是 `(heroId, skinId) → path` 的 `Skin*` 表 |
| 查询服务 | `Registry` > `Database` > `Locator` > `Repository` > `Service` > `Provider` | `Database` 来自 RimWorld `DefDatabase`；`Repository` 来自 DDD |

### 本项目的最终约定（后缀 = 固定语义，同步给 docs/项目结构.md）

| 后缀 | 语义 | 约束 | 例子 |
|---|---|---|---|
| `Config` | 静态数据的**一行**（形状） | **禁止 `from 'cc'`** | `ShipConfig` / `WeaponConfig` |
| `Table` | 静态数据的**全表** + 按 id 查询 | 全票在同一个文件里集中声明 | `ShipTable` / `ShipAssetTable` |
| `Data` | 运行时实例 / 存档，**会变** | 派生值不许落字段 | `PlayerData` |
| `Assets` / `Res` | 资源引用 | 全工程只允许这两个文件 import 资源类型 | `ShipAssets` / `ShipAssetTable` |
| `Manager` | 系统级单例 | — | `GameManager` |
| `View` | UI 面板 | — | `MenuView` |

> **`Config` 与 `Table` 的分工是这一节最值钱的一条：一行叫 Config，全表叫 Table。**
> 它顺手解决了"汇总文件该叫啥"这个老问题 —— 见第十二节。

**三条落地决定（已应用到本文档全文）：**

1. **`ShipConfig` 保留不改。** 项目里已有 `GameConfig` / `EnemyConfig` / `WeaponConfig`，
   同族一致性 > 个人偏好。要改名就整套一起改，绝不只改 Ship 一个。
2. **`ShipAssetTable` ← 原 `ShipCatalog`（拖图组件），注册表保持 `ShipAssets`。**
   理由：`Catalog` 在业界默认是 Addressables 那个**构建生成的**资源索引 JSON，
   而这里是一张**手写的**资源表。名字要能区分这两件事。
3. **`Def` 和 `Config` 不许同时出现在项目里当同义词。** 二选一，选了就写进 README。

---

> 王者荣耀 / MOBA 这类多英雄游戏真正的关键不在命名，而在这两点：
> **① 数值走配表（Excel → 生成代码/json），行为走"组合"而不是"继承"**
> （英雄 = 一张数值表 + 一组技能/Effect 的组合，不是一个 `HeroXXX.ts` 子类）；
> **② 基础属性 + 加成（`maxHpBonus` / `speedMultiplier`）分离**，绝不复制基值。
> 第二节那条"派生值现算"就是它的最小落地版。

## 十二、`ShipDefs` 改名 ⇒ `ShipTable`；资源侧两件套的关系

### Q1：`ShipDefs.ts` 该怎么改名？

**答案：`data/ships/ShipTable.ts`，导出 `SHIP_TABLE` / `getShip()` / `getShipOr()` / `cycleShip()`。**

改名本身不是重点，重点是 `ShipDefs` 这个名字**描述的是一件已经不存在的事**：

| 时期 | 形态 | 名字贴不贴切 |
|---|---|---|
| 旧（`config/ShipConfig.ts` 一个文件） | 一个文件里写死 3 个 `const SHIP_RED/GREEN/BLUE` | ✅ "Defs" 说得通 —— 它就是那堆定义本身 |
| 新（一架一个类） | 定义已经搬去了 `ShipRed/ShipGreen/ShipBlue.ts`，**这里只剩"全表 + 按 id 查"** | ❌ 它已经不产出定义了，只是把别人的定义汇总起来 |

所以它现在的真实职责是**全表**，那就该叫 `Table`，跟行类型 `ShipConfig` 构成一对：

```
ShipConfig  = 一行的形状（interface）      ShipRed / ShipGreen / ShipBlue = 三行数据
ShipTable   = 全表 + 查 ship + 循环取下一架
```

**被否掉的候选（以及各自的否决理由）：**

| 候选 | 否决理由 |
|---|---|
| `ShipConfigs.ts` | ⚠️ **同目录下会同时存在 `ShipConfig.ts` 和 `ShipConfigs.ts`** —— 只差一个字母。自动补全选错、手滑打错都不报错，`ships/` 目录从此进入"猜字母"模式。这条是硬否决 |
| `ShipDefs.ts`（保留） | 违反第 3 条决定：`Def` 和 `Config` 不许并存。它俩是同一个概念的两种叫法 |
| `ShipRegistry.ts` | 名字本身没毛病，英语系里最标准。但 `ships/` 里同时出现 `ShipRegistry`（数值）+ `ShipAssetTable`（资源）两种风格，读的人要多想一步。**想用 Registry 就把两边一起改成 `ShipRegistry` + `ShipAssetRegistry`，别混** |
| 合并回 `ShipConfig.ts` | 看起来最省事（现有 `EnemyConfig.ts` 就是 interface + `ENEMY_CONFIGS` + `getEnemyConfig` 全在一文件）。但它会让契约层反向 value-import 数据层，`import type` 一不留神写成值引用就是循环依赖。**拆开能让 `ShipConfig.ts` 变成零运行时代码的纯类型文件，循环在结构上不可能发生** |

> ⚠️ 唯一需要注意的代价：现有的取名字习惯是 `getEnemyConfig(id)` / `getWeaponConfig(id)`，
> 这里改成了 `getShip(id)` —— **不一致是真实存在的**。
> 取舍理由：`getEnemyConfig` 之所以要带上 Config，是因为那个文件既装 interface 又装数据；
> 而 `ShipTable.ts` 位于 `ships/` 目录、文件名已经代表领域，`getShip()` 读起来更顺，
> 也跟资源侧 `shipAssets.get(id)` 保持同一口味。
> **如果你更看重跟老代码对齐，保留 `getShipConfig` 完全可行 —— 别来回改名比选哪个更重要。**

### Q2：`ShipAssetTable` 和 `ShipAssets` 是什么关系？

一句话：**它是同一个数据的"写端"和"读端"，中间隔着一道 Cocos 的 prefab 墙**。

```
编辑器拖图 ──▶ ShipAssetTable (Component, 场景节点上, L5)      ← 写端：生产数据
                      │  onLoad 里 shipAssets.bind(map)
                      ▼
              shipAssets (模块单例, core/, L1)                 ← 读端：唯一的查询入口
                      ▲
                      │  shipAssets.get(id)
          ┌───────────┴────────────┐
   Player.ts (prefab 实例)   ShipSelectView (prefab 实例)
      ❌ 拿不到左边的组件，因为 prefab 内的 @property 不能引用场景节点
```

| | `ShipAssetTable` | `shipAssets` |
|---|---|---|
| 形态 | 继承 `Component`，挂在场景节点上 | 普通 TS 类单例，不挂任何节点 |
| 所在层 | L5（`managers/`） | L1（`core/`） |
| 认识 `cc` 吗 | 认识（要拖 `SpriteFrame`） | 不认识（只存 `Map<string, SpriteFrame>`，`import type` 编译后消失） |
| 生命周期 | 跟宿主节点；切场景就没了 | 跟进程；整个游戏都活着 |
| 谁调它 | **只有 Cocos 自己**（反序列化 @property） | 所有业务代码 |
| 方向 | `bind()` 写 | `get()` 读 |

**为什么必须拆成两个（重点）：**

1. **中间那道墙过不去。** `Player` / `ShipSelectView` 都是 prefab 实例，而 **prefab 内的 `@property` 不能引用场景节点/组件**。
   所以它们**在编辑器层面就没有办法**持有场景里那个 `ShipAssetTable`。
   唯一的现实办法：让 `ShipAssetTable` 主动把数据灌进一个"不在场景里、但能被任何模块 import 到"的地方 → 就是 `shipAssets`。
2. **分层守规矩。** `Player` 是 L4，只允许依赖 L0~L2。`ShipAssetTable` 在 L5（`managers/`），
   如果 `Player` 直接 import 它就破层了；而 `shipAssets` 放 L1，`Player` import 它天经地义。
3. **生命周期。** Component 挂在节点上，切场景就销毁；模块单例跟进程，一局从头用到尾。
   把"业务查询入口"绑在节点上，等于让 Player 拿一个随时可能失效的句柄。

**三条约束，防止它俩被混用：**

- 箭头单向：`ShipAssetTable` → `shipAssets`，**没有任何文件反向 import `ShipAssetTable`**（除了场景序列化本身）。
- `ShipAssetTable` 里除了"组织 Map + 缺图 warn"之外不许有业务逻辑 —— 它只是接线端子。
- 所有使用方 imports 的是 `shipAssets`，**不是** `ShipAssetTable`。grep 一下 `from '...ShipAssetTable'`
  应该只出现在场景/prefab 的序列化里，代码里出现就是犯规。

> 类比：这跟"UI 读数据"是同一个套路 —— 生产者 ===> 索引 ===> 消费者。
> Unity 里对应 Provider / ServiceLocator，Cocos 里因为 prefab 墙，只能用一个模块级单例当索引。
> 这也是为什么 `EventBus`、`GameState` 这些跨 prefab 通道全都是模块单例，不是一个 Component。

## 十三、改名后的最终文件清单

```
assets/scripts/
├── data/ships/
│   ├── ShipConfig.ts       interface ShipConfig        （零运行时代码）
```

命名对照（改前 → 改后）：

| 改前 | 改后 | 原因 |
|---|---|---|

| `SHIP_CONFIGS` | `SHIP_TABLE` | 与文件名对齐 |
| `getShipConfigOr` | `getShipOr` | 同上 |
| `ShipCatalog.ts` | **`ShipAssetTable.ts`** | `Catalog` 是 Addressables 的构建产物索引，语义不同 |
| `ShipConfig.ts` | 不变 | 与 `EnemyConfig` / `WeaponConfig` 同族 |
